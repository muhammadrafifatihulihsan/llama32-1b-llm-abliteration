# Troubleshooting

[Usage guide](usage.md) | [Panduan penggunaan](usage.id.md)

## Python or a package cannot be imported

Check that VS Code is using the environment where you installed dependencies:

```bash
python -c "import sys; print(sys.executable)"
python -m pip check
```

Select the matching notebook kernel and restart it after installing packages. Use `python -m pip` so the installer belongs to the selected Python. The project does not include a verified environment lock, so a clean dependency install may still require compatible package versions.

If PowerShell blocks environment activation, you can use its interpreter directly without changing system policy:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

## CUDA is unavailable

Run notebook 00 and check the installed PyTorch build and GPU driver. A CPU-only PyTorch installation will not use CUDA. On machines without a compatible GPU, some operations can run on CPU but model notebooks may be slow or include GPU-specific diagnostic cells.

## CUDA out of memory

Restart the kernel to release the previous model. Close other GPU workloads, then review batch sizes in `src/config.py` and the relevant notebook cells. Activation extraction also stores CPU tensors, so RAM can be a limit. Use the Colab alternative for step 02 if needed; adjust its batch-size override to fit the available GPU.

## Model access fails

Check that your account can access the configured base model and that `HF_TOKEN` is set correctly. Restart the kernel after updating `.env`. Do not paste tokens into notebook cells or commit them.

## A CSV or checkpoint is missing

Check the path in the error and the [data schema](../data/README.md). The three experiment CSVs are included under `data/`. Checkpoints can be generated by earlier notebooks or downloaded from Hugging Face following the [model instructions](../models/README.md); the source ZIP does not include them. Follow the order in the usage guide and copy Colab outputs back before continuing locally.

## Colab cannot find the project

Mount Drive first, then set `PROJECT_DIR` to the folder containing `src/` and `requirements.txt`. The `.env` file inside that folder cannot be used to locate the folder itself. The dependency-install cell uses the selected `PROJECT_DIR`.

## GGUF conversion fails

Check the llama.cpp path and install that checkout's converter dependencies into the Python environment used by notebook 07. Read the converter error before continuing. An existing GGUF file can belong to an older run; it is not proof that the latest conversion succeeded. This workflow requests F16, not 4-bit quantization.

## Ollama connection or model errors

Check the local server and registered models:

```bash
ollama list
```

Make sure `OLLAMA_HOST` points to that server and `OLLAMA_MODEL` matches the tag you created. If the model is missing, run `ollama create` from the project root using the supplied Modelfile. Repeat it after replacing the GGUF; notebook 08 skips an already registered tag. HTTP/API errors now raise exceptions instead of being scored as empty responses.

## Metrics differ or rows are duplicated

The saved runs used different input sets and runtime defaults. Your data, environment, cell order, and generation settings can change the output. See [results notes](results.md).

Notebook 01 resets the local metrics CSV, while later notebooks append. Save an external copy of any run you need before starting over, and avoid repeating append cells. The reference results are stored separately.

## Repository checks fail before sharing

The checker reports the file involved. Typical causes are stored notebook outputs, broken documentation links, or a file outside the package list. Clear notebook outputs and execution counters, save, then rerun the checker. Keep credentials, additional private datasets, and model artifacts local. If intentionally adding a new type of public file, update `public_files()` in `scripts/check_repo.py` as well.
